# План распараллеливания по субагентам

Как разбить [implementation-plan.md](./implementation-plan.md) на задачи, которые
субагенты выполняют параллельно, не конфликтуя.

## Главный принцип: сначала заморозить контракты

Поддомены связаны через типы моделей и сигнатуры портов. Если агенты начнут писать
их одновременно, ветки разойдутся по интерфейсам и не соберутся вместе. Поэтому
работа делится на три фазы: **фаза 0** замораживает контракты (один агент,
блокирующая), **фаза 1** — параллельная реализация по пакетам, **фаза 2** — сборка и
интеграция (один агент, блокирующая).

Правило изоляции: каждый агент в фазе 1 редактирует **только свой каталог пакета**.
Общие файлы моделей создаются в фазе 0 и дальше не трогаются (кроме фазы 2 при
рассинхроне контрактов).

## Граф зависимостей

```
            ┌──────────────── Фаза 0: контракты (блокирует всё) ───────────────┐
            │  модели: lexicon.Word, flashcard.Note, deckbuilder.Suggestion     │
            │  порты:  Dictionary, Cards (out) · Service (in)                    │
            │  тест-даблы: usecasetest (фейки Dictionary/Cards/Service)          │
            │  каркас каталогов + go.mod + компилируемые заглушки                │
            └───────────────────────────────────────────────────────────────────┘
                    │            │            │             │            │
   Фаза 1   ┌───────┴───┐ ┌──────┴────┐ ┌─────┴──────┐ ┌────┴─────┐ ┌────┴────┐
 (параллель)│ A:ankicon.│ │ B:lexicon │ │ C:flashcard│ │D:deckbld.│ │ E: tui  │
            │  client   │ │ wiktionary│ │   anki     │ │ usecase  │ │         │
            └───────┬───┘ └───────────┘ └─────┬──────┘ └──────────┘ └─────────┘
                    └───── C зависит от A (через заглушки методов клиента) ──────┘
                    │            │            │             │            │
            ┌───────┴────────────┴────────────┴─────────────┴────────────┴──────┐
   Фаза 2   │  F: cmd/anki composition root + go build/vet/test, фикс рассинхрона │
            └────────────────────────────────────────────────────────────────────┘
```

## Фаза 0 — контракты и каркас (1 агент, блокирующая)

Цель: репозиторий собирается (`go build ./...`) со всеми типами и сигнатурами, но с
телами-заглушками (`panic("not implemented")` / нулевые значения). После этого
контракты заморожены.

Создаёт:

- Каталоги `cmd/anki`, `internal/{lexicon,flashcard,deckbuilder/usecase,tui}`,
  `pkg/ankiconnect`; перенос текущего кода клиента в `pkg/ankiconnect`.
- `lexicon/word.go` — `Word`, `PartOfSpeech`, `Gender` (полные определения полей).
- `flashcard/note.go` — `Note`, `Field`, `Deck`, `DeckName`, сигнатура
  `IsComplete(Note) bool`.
- `deckbuilder/suggestion.go` — `Suggestion`.
- `deckbuilder/usecase` — определения **outbound-портов** `Dictionary`, `Cards`;
  **inbound-порт** `Service` (интерфейс с `AddWord`, `ScanDeck`, `Apply`, `Decks`),
  который реализует приватный `service` (заглушки) и от которого зависит TUI.
- `pkg/ankiconnect` — сигнатуры методов-действий (`AddNote`, `DeckNames`,
  `FindNotes`, `NotesInfo`, `UpdateNoteFields`) с заглушками.
- **Общие тест-даблы** (чтобы агенты D и E не разошлись по мокам):
  - `deckbuilder/usecase/usecasetest` — программируемые фейки `Dictionary` и
    `Cards` и фейк `Service` (возвращают заранее заданные значения/ошибки).
  - Их сигнатуры тоже заморожены; реализация фейков тривиальна и пишется в фазе 0.

Выход фазы 0 — единственная точка согласования (модели, порты, сигнатуры действий,
тест-даблы). Менять контракты после этого можно только через фазу 2.

## Фаза 1 — параллельная реализация (5 агентов)

Каждый агент реализует тела + тесты строго в своём пакете. Контракты из фазы 0 —
read-only.

| Агент | Пакет | Зависит от (контракты) | Делает |
|---|---|---|---|
| **A** | `pkg/ankiconnect` | — (независим) | Починить `getRequest` (чтение `{result,error}` из тела), реализовать действия |
| **B** | `internal/lexicon/wiktionary` | `lexicon.Word` | Запрос к German Wiktionary, парсер шаблонов → `lexicon.Word` |
| **C** | `internal/flashcard` (+ `anki/`) | `pkg/ankiconnect` методы, `usecase.Cards` | `IsComplete` инвариант; адаптер `anki` реализует `Cards` через клиент |
| **D** | `internal/deckbuilder/usecase` | `lexicon.Word`, `flashcard.Note`, порты | Трансляция `Word→Note`, сценарии `AddWord/ScanDeck/Apply/Decks` |
| **E** | `internal/tui` | `usecase.Service` (inbound-порт) | Bubble Tea: модель, состояния, команды, стили |

Заметки по зависимостям:

- **A** полностью независим — может стартовать сразу, даже до фазы 0.
- **C** вызывает методы клиента из A, но кодирует против их **сигнатур-заглушек**
  (заморожены в фазе 0), поэтому идёт параллельно с A.
- **D** не знает про адаптеры — только модели + собственные порты; тестируется на
  фейках из `usecasetest`. Параллелен B и C.
- **E** знает только inbound-порт `usecase.Service` — собирается против фейка
  `Service` из `usecasetest`. Параллелен D.

## Тестирование (каждый агент пишет тесты своего пакета)

Тесты — часть Definition of Done каждой задачи фазы 1, лежат рядом с кодом и не
делят файлы между агентами. Уровни:

**Unit / по агентам**

- **A `pkg/ankiconnect`** — `httptest.Server`: корректность конверта
  (`action/version/params`), декодирование `result`, проброс ошибки из поля
  `error` при HTTP 200, обработка сетевой ошибки. Фикстуры — сырые JSON-ответы
  AnkiConnect.
- **B `lexicon/wiktionary`** — table-тесты парсера на сохранённых фикстурах
  wikitext: существительное (`Genus`+`Plural`), глагол (Partizip II/Hilfsverb/
  reflexive), прилагательное (степени), страница отсутствует, часть речи не
  распознана (`Other`). Фикстуры — файлы в `testdata/`.
- **C `flashcard`** — table-тесты инварианта `IsComplete` по частям речи (полная /
  пустой Back / нет грам. поля). **C `flashcard/anki`** — `httptest.Server`:
  трансляция модель→DTO и обратно для `Add/Decks/FindIncomplete/Update`, фильтр по
  `IsComplete`.
- **D `deckbuilder/usecase`** — на фейках `Dictionary`/`Cards` из `usecasetest`:
  golden-тесты трансляции `Word→Note` по всем частям речи; сценарии
  `AddWord/ScanDeck/Apply/Decks`; извлечение lemma из Front (артикль/`sich`);
  пометка `Skipped` при «не найдено».
- **E `tui`** — чистые переходы `Update(msg) -> model` на фейке `Service`: подаём
  `decksMsg`/`lookupDoneMsg`/`scanDoneMsg`/`applyDoneMsg` и ошибки, проверяем
  состояние и команды. Терминал не нужен.

**Contract-тесты (структурное соответствие)**

Порты реализуются структурно — ничто не заставляет адаптер совпасть с портом до
сборки в `cmd/`. Поэтому каждый адаптер-агент добавляет в свой пакет
compile-time-проверку:

- C: `var _ usecase.Cards = (*ankiAdapter)(nil)`
- B: `var _ usecase.Dictionary = (*Client)(nil)`
- (внутри `usecase`) `var _ Service = (*service)(nil)`

Это ловит рассинхрон сигнатур уже на `go build` пакета, а не в фазе 2.

**Запуск у каждого агента**

`go test ./<свой-пакет>/... -race` и `go vet ./<свой-пакет>/...` — зелёные перед
сдачей задачи.

## Фаза 2 — интеграция и сквозное тестирование (1 агент, блокирующая)

Сборка:

- `cmd/anki/main.go` — composition root: собрать `ankiconnect` → `flashcard/anki`
  (`Cards`), `lexicon/wiktionary` (`Dictionary`), `deckbuilder/usecase.Service`,
  инъекция в `tui`, запуск.
- Разрешить рассинхрон контрактов, если параллельные ветки разошлись (единственное
  место, где допустимо править файлы фазы 0).

Интеграционные тесты (реальные пакеты, но внешние сервисы — на `httptest`):

- `internal/flashcard/anki` поверх `httptest`-двойника AnkiConnect, состыкованный с
  `deckbuilder/usecase`: сценарии `AddWord` и `ScanDeck→Apply` целиком на фейковом
  HTTP, без моков портов (проверяем реальную трансляцию + конверт вместе).
- `lexicon/wiktionary` поверх `httptest` с сохранённым ответом MediaWiki,
  состыкованный с `usecase`: lookup→трансляция→`Note`.
- Помечать тегом `//go:build integration`, чтобы отделить от быстрых unit-тестов.

Полный прогон и качество:

- `go build ./...`, `go vet ./...`, `go test ./... -race`,
  `go test -tags integration ./...`, `golangci-lint run ./...`.

Сквозная (E2E) проверка вручную:

- Против живого Anki + AnkiConnect (см. functional-spec): оба режима —
  добавление слова и сканирование deck — на отдельной тестовой колоде.

## Что обеспечивает бесконфликтность

- Один пакет — один агент; пересечений по файлам в фазе 1 нет.
- Все межпакетные типы и сигнатуры зафиксированы в фазе 0; агенты их только читают.
- Порты объявлены у потребителя (`usecase`) и реализуются структурно — адаптеры
  (B, C) не импортируют ядро, поэтому не зависят от агента D.
- Тест-даблы (`usecasetest`) тоже заморожены в фазе 0 — D и E мокают одинаково и не
  плодят расходящиеся фейки.
- Тесты каждого агента живут в его же пакете, фикстуры — в локальном `testdata/`,
  между агентами не делятся.
- Contract-проверки (`var _ Port = (*Impl)(nil)`) ловят рассинхрон сигнатур на
  `go build` пакета, до интеграции в фазе 2.
